## When to start the HTLC atomic swap (Andjroo's question)

**Short answer: the foundation is built and merged, and now is a reasonable time to start —
but start on TESTNET, as a separate focused effort, not folded into the wallet-polish loop.**

### What already exists (on `main`, behind the `bitcoin-leg` feature)
The swap was built as its own track and its core is **already merged to main** (not stranded
on a feature branch — `feat/mesh-swap` and `feat/usdc-polygon` merged long ago). What's there:

- **Wire + state machine + atomicity proof (F2–F4, done):** swap message types `0x40–0x44`
  (`swap_wire.rs`), the height-anchored timelock state machine with the `Δ_safe`
  safety gate that *refuses to fund a swap whose timelocks can't be made safe over a
  high-latency mesh* (`swap.rs`), and the `SwapLeg`/`MockLeg` e2e proving **no one-sided
  settlement is ever possible** across the happy path + 4 adversarial paths.
- **The FFI engine object (`swap_ffi.rs`, behind `bitcoin-leg`):** `SwapEngine` with
  `new_initiator`/`new_responder`/`accept`/`fund`/`observe_*`/`reveal_and_claim_btc`/
  `claim_nim_from_btc_claim`/`refund` — the app-facing surface a Swap UI would drive.
- **Nimiq HTLC serialization (F1):** funding tx + redeem content byte-exact vs `@nimiq/core`
  2.7.0; the resolve **proof** was the open sub-cycle (a core-rs-albatross byte-layout gate).
- **The swap UI slice-1** already ships in the app today (the Swap sheet: NIM→BTC/USDC
  toggle, the mesh-discovery beat, the HTLC phase timeline) — but it's **SIM-driven**, clearly
  labeled "no real funds move yet." It is the shell waiting for the real engine bridge.
- **Full doc set** in `docs/swap/` — `SWAP.md`, `SWAP-LOOP.md`, `SWAP-ENGINE.md`,
  `BTC-KEY-SEAM.md`, `WALLETS.md` (persistent testnet NIM+BTC wallets), `AMOY.md`/`USDC-GAS.md`
  (the Polygon/USDC track).

### What it takes to actually try one — the readiness checklist
The swap is a bigger, more dangerous surface than payments (two chains, two funding txs, a
secret reveal, timelocks). Before a first live attempt:

1. **Finish F1's resolve-proof** so a real NIM HTLC can be *claimed* and *refunded* byte-exact,
   not just funded. (Funding + redeem content are already byte-exact; the timeout-resolve proof
   was the open item.)
2. **Bridge `SwapEngine` through Swift** (the "slice 2" that was always next): wire the
   already-exported FFI object to the existing Swap sheet, replacing the sim timeline with the
   real `Proposed→Accepted→Funded→Revealed→Settled` states. Build the framework with
   `bitcoin-leg` (like we just did for `gateway-rpc`).
3. **Pick the first pair + network.** NIM⇄BTC on **testnet** is the F0 target (persistent test
   wallets already funded per `WALLETS.md`). The real Bitcoin leg needs a BTC node + testnet
   coins — that's the `needs:owner` gate. NIM⇄USDC-on-Polygon (Amoy testnet) is the other
   track and may be simpler to demo since the gas-abstraction work is further along.
4. **Two participants.** A swap needs a counterparty node. Same options as the mesh test: the
   Mac can run a scriptable **swap responder** (a rig was noted as the clean path — drives the
   money-path without two phones), or your son's phone as a second device.
5. **Respect the invariant.** No seed / no preimage-before-reveal ever crosses the FFI, the
   mesh, or a log. The preimage is revealed *only* inside a signed claim tx that is meant to be
   public. Testnet first; mainnet + real BTC funds are Andjroo-gated, never autonomous.

### Recommendation
Treat the swap as **its own next session**, kicked off deliberately, with this order:
1. Finish F1 resolve-proof (pure Rust, testable headless — safe to auto-advance).
2. Bridge `SwapEngine` to the Swap sheet on **testnet** (the sim→real swap UI).
3. Run a **testnet** NIM⇄BTC (or NIM⇄USDC-Amoy) swap end to end with the Mac as the
   scripted counterparty — the swap analog of the mesh-payment proof we just did.
4. Only then discuss a mainnet / real-BTC attempt, gated and Andjroo-driven, exactly like we
   did for the mainnet payment.

The mesh-payment work we just finished is the load-bearing layer under all of this — the swap
negotiation, funding txs, and secret reveal all ride the *same* mesh transport that now
provably works with real money. So the hard part (a real mesh) is done; the swap is the next
capability built on top of it.
