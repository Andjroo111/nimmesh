# ADR-0002 — BLE layer: thin native radio shim driven by the Rust core (UniFFI foreign traits)

**Status:** accepted (2026-06-26) · **Context:** resolves the open radio question in **G5**, building on ADR-0001 (native Swift+Kotlin sharing a Rust core via UniFFI). ADR-0001 fixed the *core* in Rust and assumed a thin native BLE shim; ADR-0002 decides, on merit, that the BLE **radio itself stays native** (it does NOT move into Rust) and specifies the callback boundary and the build host.

## Decision

Keep the BLE radio in a **thin native shim** — Swift `CoreBluetooth` on iOS, Kotlin `android.bluetooth.le` on Android — and let the **Rust core own everything above the byte-stream transport seam**. Wire the two together with **UniFFI foreign traits** (`#[uniffi::export(with_foreign)]`), the modern superset of callback interfaces, as two objects pointing at each other:

- **`BleRadio`** — a *foreign* trait the shim implements (Swift/Kotlin). Rust holds `Arc<dyn BleRadio>` and calls *out* to it: `start_advertising`, `start_scanning`, `send` (fire-and-forget), `disconnect`, `stop`. This is the only surface the radio layer must provide.
- **`MeshNode`** — a Rust `#[derive(uniffi::Object)]` the shim calls *in* to on every BLE event: `on_peer_connected`, `on_peer_disconnected`, `on_packet_received` (the hot path: decode→dedup→relay/gateway), `on_send_result`, `submit_local_tx`. All G4/G6/G7 logic (codec, TTL/hop relay, LRU dedup, GCS store-and-forward, gateway queue, Noise) lives behind these methods.

The shim is mechanical: each delegate callback maps to one `node.on_*` call; each trait method maps to one CoreBluetooth / `android.bluetooth.le` action. **Radio-in-Rust (objc2-core-bluetooth / JNI / btleplug / blew) is rejected.**

**Build host:** the **Mac Mini is the primary autonomous build host** (full Xcode + Android SDK/NDK/JDK installed locally); **GitHub Actions Linux is the free Rust-core gate and macOS is a metered clean-room backstop** gated to native-touching PRs; **Andjroo's Mac + Apple Developer account own all iOS signing/device/distribution and all physical mesh-interop tests.**

## Why

1. **The only hard thing is OS-governed, so Rust buys nothing there.** Background survival lives in Info.plist `bluetooth-central`/`bluetooth-peripheral` modes, CB **state restoration**, and the Android `connectedDevice` **foreground service** — all language-agnostic OS machinery. Moving the radio into Rust cannot improve background survival; it can only make the foreground service and the `willRestoreState:` delegate (which must be reconstructed deterministically across process restarts) more fragile, on the least-trodden path, with no precedent.
2. **Android structurally forces a native shim regardless.** Android's ART does **not** implement the JNI `DefineClass` function — you cannot subclass a Java class from native at runtime. The entire `android.bluetooth.le` callback surface (`ScanCallback`, `AdvertiseCallback`, `BluetoothGattServerCallback`) is delivered through **abstract classes you must subclass**, so every callback path requires hand-written Kotlin callable-wrappers forwarding via `RegisterNatives`. Permissions must originate from an Activity and the foreground service is a manifest lifecycle component. Rust-maximal would write nearly all the Kotlin it was trying to avoid, plus a brittle JNI marshalling layer on top.
3. **The proven precedent keeps the radio native; the Rust BLE crates don't fit.** Bitchat — the exact protocol this repo forks — keeps the radio fully native on both platforms (Swift `BLEService` with state restoration; Kotlin `BluetoothMeshService` with a foreground service). `btleplug` is explicitly **central-only and refuses peripheral/advertising**; `blew` is alpha, Iroh-tuned, Tokio-only, with no iOS-background story. Conversely, **Rust-core + UniFFI foreign-trait callbacks on mobile in background is production-proven** (Matrix Rust SDK, Firefox).
4. **The testability win is decisive.** Because `BleRadio` is a plain trait, it is implemented in **pure Rust** for tests (`MockRadio`) and N `MeshNode`s are wired into a virtual topology with controllable latency/loss/partition. The whole GOAL.md demo loop (`sign → flood → TTL relay → dedup → GCS store-and-forward → gateway → receipt → settled`) runs headless under `cargo test`, deterministic, no phone — the same `kind: mock | real` seam RISKS.md Part A already names (`MockMeshTransport`). ~95% of the codebase is unit/property/fuzz-testable; only the ~1.5–2k-LOC radio shim needs a device, and protocol changes touch one Rust file and propagate byte-identically to both platforms.

## Alternatives rejected

- **Rust-maximal radio (objc2-core-bluetooth on iOS, JNI on Android).** Adds an FFI layer over OS BLE APIs, buys **zero** improvement on background survival (OS-governed), rides the least-exercised peripheral+advertise branch of objc2, and on Android is **forced to write the Kotlin shim anyway** (no `DefineClass` + permissions + foreground service). Splits async callbacks across Rust↔objc2↔CoreBluetooth and Rust↔JNI↔ART, loses native BLE tooling, and inherits autorelease/threading crash classes with no compiler help. Scored ≈ 11/25 vs the thin shim's ≈ 21/25.
- **Rust BLE crates (btleplug / bluster / ble-peripheral-rust / blew).** Central-only or peripheral-only or stale or alpha; desktop-first; no mobile-background story. (Already rejected in ADR-0001; reaffirmed.)
- **GitHub Actions macOS as the *primary* build host.** Metered at ~$0.062/min (10× the Linux tier, not in the private-repo free tier) and slower than the M4 Pro Mini. Keep it as a clean-room reproducibility backstop on native-touching PRs only.
- **Putting Andjroo's iOS signing certs in CI to "fully automate" iOS device builds.** A `needs:owner` security decision, not the loop's. iOS device signing stays on Andjroo's Mac.

## Consequences

- **Native shim size:** iOS Swift ≈ 600–900 LOC; Android Kotlin ≈ 800–1100 LOC — pure radio, the protocol/relay/dedup code that bloats Bitchat's transport files now lives once in Rust.
- **Four UniFFI-callback gotchas to engineer for:** (a) **Never call `radio.send` synchronously from inside `on_packet_received`** — on iOS that re-enters CoreBluetooth's own dispatch queue; `on_packet_received` must only cheaply enqueue to an internal channel and return, and a Rust worker drains it, applies the 10–220 ms relay jitter off-thread, then calls `radio.send`. (b) **Break the cross-language refcount cycle** (`MeshNode` holds `Arc<dyn BleRadio>`; the shim's delegate holds the `MeshNode` handle) by making one edge weak — Swift `weak var node`; Kotlin explicit `.destroy()`/lifecycle tied to the foreground service (no deterministic GC → a leaked handle pins the BLE stack). (c) **`send` is fire-and-forget**; the real CB/GATT write outcome returns async via `on_send_result(peer, ok)`; wrap every shim callback defensively (an unguarded throw during a flood burst can surface `UnexpectedUniFFICallbackError` and abort the process). (d) Drive validity-window GC off received head-beacons (`0x32`), not a precise local clock — iOS background coalesces timers.
- **Performance is a non-issue:** one `RustBuffer` copy per ~256 B packet (PROTOCOL.md: one BLE packet, zero fragmentation) is sub-microsecond, orders of magnitude under BLE's ms cadence; the radio is the bottleneck, never the boundary (`echo_bytes` canary already proves the `Vec<u8>` path round-trips 0–255).
- **Honest background limit unchanged:** the iOS-background → Android-central overflow-area 128-bit-UUID dead spot is a hard BLE-platform fact no architecture fixes; mitigated by CB state restoration, the Android foreground service, and the "keep ≥1 device foregrounded" UX.
- **Build/host consequences:** install full Xcode + Android SDK/NDK/JDK on the Mini; add the Rust cross-targets it lacks (`aarch64-apple-ios`, `aarch64-apple-ios-sim`, `x86_64-apple-ios`, `aarch64-linux-android`, `armv7-linux-androideabi`, `x86_64-linux-android`, `i686-linux-android` — only `aarch64-apple-darwin` is installed). G5 build scripts must export `DEVELOPER_DIR`, `ANDROID_HOME`/`ANDROID_SDK_ROOT`, `JAVA_HOME`, and `~/.cargo/bin` explicitly (the launchd/agent-shell env trap), and run `xcode-select -s /Applications/Xcode.app` once to flip off CLT. Keep Xcode lean (~15–20 GB) by building against the `iphoneos` + `iphonesimulator` SDKs without a bootable simulator runtime — a simulator has no real BLE, so the loop never runs iOS code. Each cycle the Mini builds the Rust core, the unsigned iOS `.xcframework`, the installable Android debug APK, and compile-gates the iOS device build (`CODE_SIGNING_ALLOWED=NO`). All iOS signing, UDID registration, TestFlight/distribution, Android *release* signing, and every physical mesh-interop test stay `needs:owner`.
